# Website implementation

The `code198x/website` repository owns the Astro site, content collections, components, routes and deployment. Its package manifest and lockfile specify tool versions; its workflows specify build and publication behaviour. Documentation describes responsibilities, not a second dependency manifest.

## Rendering and design

The current site uses Astro 7, MDX and the Sätteri Markdown processor. Code highlighting uses the site's `code198xHighlightPlugin` and `shiki-highlight-api`, with theme-aware CSS Custom Highlights. Preserve the current rendering path when adding a code component; do not introduce a competing highlighter or gratuitous per-token markup.

Use the established family palette, spacing and components. Nebula Sans serves headings and interface text, Literata serves reading text and captions, and JetBrains Mono serves code and data. Existing editorial templates also use Literata for display headings; follow the relevant template rather than applying a blanket font replacement. Use sentence case. Decorative system motifs belong around the reading experience, not behind text or essential controls. Maintain legible contrast, keyboard focus, responsive layouts and reduced-motion support.

The colophon combines curated tooling/typeface credits with contributor data generated by `scripts/build-colophon.mjs`. Contributor updates are reviewed source changes, not live network lookups during rendering. Keep credits factual and inclusive; do not rank contributions by commit totals. Check that script's repository inputs when changing coverage.

## Content and runtime

[Content model](../specifications/content-model.md) describes collections and state; [Information architecture](../specifications/information-architecture.md) describes routes. Use existing components before creating alternatives. The [component assessment](curriculum-components.md) separates available tools from proposals for the new curriculum direction.

`CodeFromFile` reads sample sources. Build scripts prepare downloadable outputs from those sources. `AssembleAndRun` provides an optional Spectrum assembly loop with the family assembler and emulator packages. The in-page tool must retain understandable errors, build instructions and downloads; browser execution is not hardware verification.

Native media decoding uses Play198x WebAssembly. Inspect `scripts/build-wasm.mjs`, its expected Play198x workspace and the workflow before promising that a clean local checkout can build it. Site tests may need that generated decoder too.

## Validation and publication

Use the scripts in `package.json` and [Site testing](site-testing.md). `npm run build` runs the unit suite and content checks, builds Astro and creates the Pagefind index. Targeted checks are useful during authoring; the required build remains necessary for publication. Inspect generated pages when changing their layout or interactions.

The Pages workflow builds first and announces newly live feed entries only after successful deployment. Date-gated publishing also runs on the daily rebuild. The Discord path computes a feed difference, prepares validated payloads and retains the item list as a workflow artifact. See [Discord announcements](discord-announcements.md) for delivery limits and recovery.

Development tools run on the host. Downloaded or embedded target programs still have the capabilities of their stated machine configuration. Keep that distinction visible in setup instructions and examples.
