# Meet BASIC: lesson and source mapping

**Status: implementation plan for the [agreed module direction](meet-basic.md). A1–A3 have draft lessons and verified sample checkpoints; publication is blocked on the native save/reopen workflow. The remaining arcs are not yet implemented.**

The four arcs are agreed. The lesson boundaries below are a concrete authoring plan, adjustable when source development or reader testing reveals an overloaded step. The fifteen working lessons are not a required count. This plan replaces the combined progression of feature demonstrations followed by substantially repeated early projects; it does not append another course to them.

## Proposed lessons and runnable checkpoints

### Arc A — a greeting becomes Story Builder

| Lesson | Checkpoints and local explanation | Reuse and necessary changes | Check before moving on |
|---|---|---|---|
| **A1 — Make the Spectrum answer** | Run an immediate greeting; store a numbered greeting and run it; add and replace a second line. Explain keyword entry, quotes, command versus stored instruction, ascending line order, listing and editing. | Merge M01 and the insertion/replacement examples of M02. Write the complete host-key and editor-mode instructions, including `RUN`, `LIST`, editing and recovery from a mistyped line. A line number selects a BASIC line; do not imply it is a RAM address. | A reader types, runs and changes the greeting from the documented 48K start state. Check inserted and replaced lines run in the explained order. |
| **A2 — Remember a name; keep the program** | Store a name in `n$`; print it with surrounding words; change the value; save the small program, clear/reopen the target and load it again. Explain storage, `$`, the semicolon and the distinction between a variable's value and its name. | Combine the relevant parts of M03/M04 with M14, using the greeting rather than the old title-card source. Move the unknown-variable diagnostic from M15 here. New checked save/load instructions must identify the actual emulator tape workflow and destination file. | The loaded program lists and runs correctly, then accepts another edit. Show the difference between saving source/program data and saving a machine snapshot. Label intentional error examples separately from successful checkpoints. |
| **A3 — Ask, then use the answer** | Replace the fixed name with `INPUT`; ask for two further words; combine them into a sentence. Explain that `INPUT` waits and stores an answer, and distinguish quoted text from a string variable. | Merge M05's text example with S01–S02. Start with the preceding greeting; do not import the existing multi-command colour setup without teaching it. Choose sentence wording that does not require an unexplained article-selection algorithm. | Different inputs produce corresponding sentences. Investigate empty and long answers and document the accepted behaviour. A prompt must make clear what sort of answer is useful. |
| **A4 — A story worth sharing** | Add a setting and another event; arrange readable lines and a plain text title; save the finished story and let someone else run it. S04's nearly unchanged output is an experiment within this lesson, not a whole separate lesson. | The toy can be used without spoken instructions. The saved program reproduces the revised story; output stays legible for the documented inputs. It needs no score, loss or automatic replay. |

A2 deliberately introduces saving before the larger story. If the save workflow needs more room, split it at its natural boundary rather than returning it to the end of the module. `LET` is explained before `INPUT` supplies a value; readers also see that `INPUT` performs the assignment itself.

### Arc B — Lucky Number

| Lesson | Checkpoints and local explanation | Reuse and necessary changes | Check before moving on |
|---|---|---|---|
| **B1 — Give a useful clue** | Begin a small new program with a known secret and one numeric guess. Add equal, lower and higher responses separately. Explain numeric input and each comparison, using exact test guesses before adding chance. | Reshape M05's number example and M06's fixed-secret comparisons. L01 is the later destination, not the starting listing. Keep an explicit known secret, initially 7 in a stated 1–10 range. Explain the lack of an `ELSE` clause through the actual independent tests. | Guess below, equal to and above the secret. Exactly the appropriate response appears. Distinguish an input report from a game-rule rejection. |
| **B2 — Keep guessing** | Add a return to the input after an incorrect guess; stop on a correct one; add a counter and explain its initialisation. Reject out-of-range and non-whole-number guesses without consuming an attempt. | M08 step 1 supplies the loop structure; M06 step 3 supplies condition-combination examples. Teach `INT` first as part of the whole-number check if used here. Split compressed statements during first explanation, especially conditional lines. | A known series of guesses gives the predicted count. Test the two range boundaries and values just outside them, a fractional guess and a correct first guess. Explain why returning to input must not reset the secret or count. |
| **B3 — Choose a new secret** | Replace the known secret with a random integer in the same stated range; derive multiply, `INT` and offset; distinguish a repeated test setup from ordinary play. | Combine the random-expression explanation from M08 step 3 with L01. M08's counted-loop demonstration is not a prerequisite here: inspect individual generated values before teaching `FOR` in Oracle Stone. Keep the first random range small; changing it to 1–100 is an explained variation. | Exercise the endpoints through known-secret test cases and inspect generated values for bounds. A finite sample does not prove fairness or that every possible value occurs. Verify any fixed-seed procedure in the chosen environment. |
| **B4 — Feedback and another round** | Add legible colour choices and short directional sounds alongside the words; offer another round with `INPUT`, resetting secret and count together. Keep a final attempt count. | Reuse selected L03 feedback and M10/M11 explanations. L04–L05 provide finishing ideas, but their final source does **not** contain replay: write and explain it. Keep hot/cold distance bands from L02 and elaborate ratings as optional variations, with their own local maths. | Play two rounds, including a correct first guess. Confirm reset and exit; retain the clues with audio muted. Check sustained wrong guesses for unwanted scrolling, and distinguish upper-screen output from the input strip. |

B4 can contain separate saved states for colour, sound and replay, or split into lessons if the explanation warrants it. It must not jump from the plain loop to the current decorated final listing. A text replay prompt avoids needing fresh-key handling before the movement arc.

### Arc C — Oracle Stone

| Lesson | Checkpoints and local explanation | Reuse and necessary changes | Check before moving on |
|---|---|---|---|
| **C1 — Choose an answer** | Start a new short listing with an invitation, a question and three authored responses selected by a random integer. Add a plain answer heading and readable colour. | Compress O01/O03/O05 around their actual work. Reuse `INPUT` and random selection with brief local recall. Begin with three mutually exclusive choices; ten answers are optional content. The source uses chained `IF`s, not an array. | Force each selection in a labelled test version. Explain that the question is stored but not interpreted: changing its words does not determine the verdict. |
| **C2 — Give the answer a rhythm** | Compare an immediate answer with a short pause and repeated visible marks; replace repeated statements with a `FOR`/`NEXT` loop. Audition an optional brief sound and vary the repeat count. | Combine O02 with M07 and M11. First repeat the same mark or cue; using the loop variable to change pitch is an extension. Explain the loop's start, end and repeated body, and what resumes afterwards. | Trace an exact small repeat count and compare with observation. Keep a visible cue with sound off. Observe key interactions with `PAUSE`; do not promise an uninterruptible or exact elapsed delay. |
| **C3 — Write the repeated job once** | Put the same simple title/separator block on question and answer screens; show the duplication; extract that exact block into a `GO SUB` routine and return to each caller. Complete and save the toy. | Combine M08 step 2 with O04/O06. Reuse the motivation for a repeated title, but replace the existing `LEN`/centred-title helper with a fixed, fully explained job. This arc introduces counted repetition and a routine without pre-teaching Bright Spark's sequence representation. Defer the chamber's block graphics, flashing answer and general-purpose centring helper. They can be optional later experiments once their code has been explained and checked.

### Arc D — move a marker

| Lesson | Checkpoints and local explanation | Reuse and necessary changes | Check before moving on |
|---|---|---|---|
| **D1 — Put it somewhere** | Draw a marker at an explicit row and column; store the position in variables; change each coordinate separately. Keep instructions in a different part of the screen. | Use M09 step 1 and selected edge examples from step 2. Start a new minimal listing instead of carrying the old title-card framework. Distinguish the physical character grid from the ordinary BASIC print area and reserved input/report area. | Check row/column order, origin and all chosen play-area limits. The marker and instructions remain in their intended areas. |
| **D2 — Make it move** | Move across a bounded row automatically, first observing a trail, then erasing the old cell before drawing the next one. Add a deliberate pause and stop or restart at the chosen boundary. | Reshape M13's single sample. Separate its combined loop/drawing/timing behaviour into inspectable steps; reuse the counted loop from C2. No pixel graphics or custom character definition is needed. | Compare old and new positions and the boundary transition. Observe the actual movement and explain that work plus waiting determines pace. Do not present flicker as proof that BASIC must be abandoned. |
| **D3 — Let the player steer** | Replace automatic movement with a continuing loop that reads `INKEY$` once into `k$`, adjusts a proposed position for left/right input and checks the boundary before drawing. Add vertical movement only as an optional extension. | Use R01's polling explanation and M13's draw/erase idea. **New sample sequence required:** neither current source supplies keyboard-steered movement. Explain `INPUT` versus polling and why an irrelevant key leaves the position alone. | Tap, hold and release each control; press an unrelated key; move into both edges. Ensure the displayed position agrees with stored state and invalid movement never reaches `PRINT AT`. |
| **D4 — One press, one step** | Compare held-key movement with a version that accepts one movement event, waits for release and then accepts the next. Add a documented quit key and a clean return to editing. Save and reopen the experiment. | Write the fresh-press state explicitly; do not copy R01's single wait loop as a complete press-and-release solution. Retain the held-key version as a comparison checkpoint. Quit works from the documented states; no key carried over from launching creates an unexplained move. |

The endpoint is a small controllable experiment, not an extra game with enemies, scoring and levels. The two input behaviours provide useful preparation for Bright Spark and Touchdown without implementing either game's rules in advance.

### Wording and scope

Use a connection such as: “`LET tries = tries + 1` reads the old count, adds one and stores the result. Foundations' [A Box That Grows From Itself](https://code198x.com/foundations/working-it-out/unit-02/) traces that change one step at a time.” The local sentence supplies the idea and the link explains the benefit of following it. Avoid “as you learnt in Foundations” and unqualified “see Foundations” links.

Do not use generic interpreter-speed or frame-rate claims from a shared explanation as evidence about these programs. Performance, keyboard polling, saving and sound need their own target-specific checks. Likewise, do not repeat universal game-design or reader-blame claims merely because they appear in an otherwise useful Foundations unit. The charter governs the new wording.

The handoff to **Bright Spark** should identify [A Box That Holds Many](https://code198x.com/foundations/structure/unit-01/) for ordered collections and [Telling a Job What to Work On](https://code198x.com/foundations/structure/unit-03/) for passing information to reusable work. These are later connections, not extra primer prerequisites. Bright Spark must explain its chosen string representation and how variables supply data to a BASIC subroutine; pseudocode parameters, local names and returned values do not describe the behaviour of `GO SUB`/`RETURN` automatically.

When the revised lessons are published, add a small number of reciprocal application links from the relevant Foundations units: the input example to Story Builder, repeat-until to Lucky Number, and the named-job example to Oracle Stone. Link to the actual published checkpoints once their routes are settled. Do not add links now to proposed A/B/C/D identifiers, or turn each Foundations lesson into a directory of every system example.

### Connection checks during authoring

For each selected link, verify its destination, title and relevant explanation against the current page; check any section anchor after edits. Read the BASIC paragraph with the link omitted: it must still explain enough to perform the next step. Where familiar notation has changed meaning, show the difference explicitly. Add reciprocal links only after the target exists, and check the generated pages as part of the route migration.

## Optional material and deferred concepts

Dice Roller can be offered beside Lucky Number, but it must locally explain `FOR` if reached before Oracle Stone. Its later dashboard and chart must likewise explain coordinates and scaling rather than silently require the movement arc. The short optional outcome is a bounded set of rolls and counts; the live chart is a later extension. Six numeric tallies are a deliberate simple representation, not a rule forbidding arrays elsewhere.

Keep Reflex outside the required route. Before revising it as a timing project, specify false starts, signal timing, the measured quantity and clock, and input boundaries. The current source counts loop iterations; renaming that count as milliseconds or retaining arbitrary speed ratings would not repair it.

Keep `PLOT`, `DRAW`, `CIRCLE`, `CHR$`, `FLASH`, string indexing, general-purpose centring and custom graphics out of the required primer unless an actual stage needs one and teaches it. Preserve useful pixel-coordinate explanations in a discoverable reference/experiment; they can support Touchdown later. Bright Spark must introduce `LEN`, sequence indexing, `STR$`/`VAL` and its panel routine locally. The original primer's rainbow-text example already indexes a string, so it cannot move into the new opening unchanged.

Debugging is distributed: A1 covers entry and editing, A2 variable reports and save recovery, B1/B2 branching and counters, C2/C3 tracing and return points, and D2–D4 position and input discrepancies. M15 remains a useful reference, but is no longer the first opportunity to investigate a fault. Avoid the blanket instruction to suspect the reader first: program, setup, tools and explanations can all be wrong.
