# Profiling — a practice across games and machines

**Status:** Source-audited teaching progression and bounded exercise proposals. No new benchmark or lesson implementation is claimed. Applies the [curriculum](../curriculum.md), [audio progression](audio-progression.md) and [timing and interrupts plan](timing-and-interrupts.md). Those documents retain ownership of audio scope and interrupt contracts; this document owns measurement practice and its placement.

Our recurring practice is **observe a problem → measure it → explain it → make a targeted change → measure again**. Start with a missed promise to the player, not a demand to make every routine faster. Audio supplies concrete deadlines, alongside input response, animation, drawing and loading.

## Two different subjects: guest and host

**Guest profiling** measures the original program in emulated machine time: CPU cycles or machine ticks, instruction paths, contention, DMA, interrupt latency, note onsets and game commits. Name the unit. A master tick is not automatically a CPU cycle; convert using the reported clock and machine configuration. An emulator result describes its model and build, not automatically original-hardware validation.

**Host profiling** measures the emulator or browser application on the modern computer: sampled CPU stacks, allocations, rendering work, audio delivery and wall-clock frame times. It can explain why emulating a correct guest takes too long. It cannot tell us how many Z80 cycles the guest routine required. A host can underrun audio while the guest schedule is correct; a fast host can emulate a guest that misses its own deadline perfectly faithfully.

Keep separate captures and labels. In a host experiment, hold the guest program and guest input sequence constant; in a guest optimisation, hold the emulation configuration constant. Compare both only when the question requires it. Browser inspector refresh rate, host display rate and guest display rate are different observations.

## Period techniques, chosen for the machine

| Target | Appropriate visible measurement | Limits and complementary accounting |
|---|---|---|
| Spectrum | Change the border around a bounded section via the existing output-port contract; restore the original value. Compare raster position/stripe extent with an execution trace. | Preserve speaker/tape output bits: an unmasked diagnostic write can itself change sound. No built-in readable raster-position register equivalent to the C64’s; use model timing or verified external capture. Count Z80 branch paths, contention, interrupts and waits. |
| C64 | VIC-II border `$D020` or background `$D021` markers; read raster position using `$D011`/`$D012` with a coherent wrap-aware method | A raster-line measurement has limited resolution and can wrap. VIC bus stealing/badlines, sprites, IRQs and branch/page-cross costs can defeat a bare instruction sum. Preserve the game’s colours and raster effects. |
| NES | Prefer a guest RAM event log and emulator trace for the beginner exercise. A deliberate PPU palette/backdrop marker needs its own safe rendering/PPU-access setup. | There is no Spectrum-style border register or general current-scanline register. Do not insert arbitrary `$2007` writes mid-render to measure a routine. Count branches/page crossings, NMI overhead and DMA; keep the VBlank transfer deadline distinct from the whole frame. |
| Amiga | Write a chosen colour register such as COLOR00 for a visible background marker in a controlled display; observe beam position through VPOSR/VHPOSR | This is not an equivalent independent Spectrum border facility. Copper writes can overwrite the marker and the picture may use that colour. Account for CPU model, Chip RAM arbitration, display/audio/blitter DMA and interrupts. A Copper-scheduled marker timestamps the Copper, not automatically the CPU section. |

Begin with a rough visible question, then use a finer measurement when needed. A stripe is useful evidence, not a universal stopwatch. Calibrate marker writes and log operations; compare with instrumentation disabled. Logging into a fixed buffer and reading it later avoids printing in the measured loop, but still consumes guest time and memory.

Instruction-cycle accounting begins with one actual executed path. Add taken/untaken branches, loop limits and data-dependent exits; identify a plausible worst-case path separately from the most frequently used one. Use architecture instruction timing and machine bus rules. Worst observed cost in a finite trial is not a proof of worst-case execution time. On machines with contention/DMA, explain why a static instruction sum and elapsed machine time may differ.

## Stages mapped to real projects

Each row repeats the same observe–measure–explain–change–remeasure practice at greater depth. Shared explanations can live in The Craft; readers should not need to complete a profiling course before making their first game.

| Stage and location | Small exercise | Learner outcome and evidence |
|---|---|---|
| 1. Observe without a profiler: Bright Spark unit 02; C64 Bleeper; Dash jump/collect cues; Flock unit 11 | Compare a short/long cue or repeated trigger while keeping the game action fixed. Name the symptom: response delay, merged articulation or a missing cue. Inspect the relevant counter/state. | Distinguish an intentional sound duration from a performance failure. Keep the original cue, prediction and observation. No host profiler or interrupt rewrite. |
| 2. Reveal one cost: Meteor Storm unit 20; Starfield unit 17; Dash unit 14; Flock units 11/17 | Bracket drawing or a player update. Compare the common path with new-note, HUD-change or retrigger paths, one at a time. Predict instruction work before measuring. | Explain what the interval includes and why one path costs more. Retain guest units, code/data identity, min/median/max and sample count, not just average FPS. |
| 3. Cause and diagnose a slow path: same games | Enable one reversible experimental switch: extra render preparation, redundant HUD work or repeated phrase decoding. Keep intended state changes and sound events identical. Activate it at a reproducible event. | Locate the delayed event in time. An expensive routine elsewhere in the frame is not automatically its cause. Compare the normal frame with the exceptional one and identify the causal dependency. |
| 4. Repair under a deadline: Meteor Storm rendering; planned SID Symphony; Dash/Thunder Run; Flock/Onslaught | Hoist repeated work, defer non-urgent drawing or prepare a bounded request before the handler. Use the timing plan’s deliberate overload/repair protocol. | Compare deadline misses and maximum observed lateness before/after. Hardware audio may simply sustain while a note event arrives late; separately investigate beeper edge timing. Verify input, collisions, score, musical phrasing and ownership. |
| 5. Representation and memory: Meteor Storm drawing tables; deferred Tail Chase/Volley revisits; later C64 Catacombs/Maelstrom, NES Thunder Run, Amiga Onslaught | Compare computation with a lookup table, duplicate data with compact patterns, or repeated drawing with remembered state. Hold the required result constant. | Report RAM/ROM/code growth, decode cost, clarity and restrictions alongside speed. A smaller representation may be slower; a faster renderer may impose a stricter background contract. |
| 6. Deeper diagnosis: later machine projects and optional tooling companions | Use verified conditional stops, bounded traces, inclusive/exclusive routine costs and interrupt-event timing. Investigate a rare path without keeping a full trace on forever. | Choose a measurement that can falsify the hypothesis; recognise truncation, changed instrumentation cost and incomplete call attribution. Advanced facilities are optional depth. |
| 7. Host performance: optional emulator/browser companion to any of these games | Run the same guest fixture while capturing host CPU/frame time; then investigate a host bottleneck or allocation burst, without changing the guest program. | Explain a slow emulator separately from a slow original game. Preserve guest-cycle evidence alongside the separately labelled host capture. This does not become a prerequisite for the machine track. |

## First practical profiling exercise: Meteor Storm’s drawing cost

**Proposed companion to unit 20**, building on the existing render-budget experiment; it does not displace the already queued Bright Spark lesson work. This is the first dedicated profiling exercise because the game already has a measured problem, accepted behaviour, a rendering change and a verification route.

1. **Observe:** replay a fixed keyboard-driven passage with boost, including sparse and busy object states. Read the existing `frame_delta` as time between its defined updates, not input-to-screen latency. Preserve the accepted program and fixture.
2. **Measure:** identify the actual renderer entry/exit and its callers from the checkpoint source. Capture a bounded guest-time window, plus per-update deltas. Where the native Spectrum `profile_cycles` build is available, load matching Debug198x data and declare validated routine ranges; retain interrupt/HALT/partial buckets separately. Otherwise start with border markers and a fixed RAM log, stating their resolution and cost. Do not invent start/end symbols before reading the assembled listing.
3. **Explain:** compare one and two simulation steps per outer update. Relate drawing calls, active objects and elapsed cost. A large HALT total can be deliberate waiting, not a routine to optimise. A whole-run hot-address table needs the event log to explain the late update.
4. **Introduce one expensive path:** in a separate checkpoint, repeat render preparation into scratch state on a chosen busy update. Do not blindly draw an XOR sprite twice: that can erase it and change correctness. Keep collision tests, simulation count, RNG consumption and inputs unchanged. Bound the extra work and label it experimental. Increase it only enough to cross the chosen deadline; record the cost rather than assuming a slowdown.
5. **Repair:** remove the redundant preparation or reuse the prepared result once. Compare at least baseline, fault and repair with the same fixture and instrumentation. Then confirm the repair with markers/logging disabled. If measuring the historical render-scheduling comparison too, preserve its stated XOR/background invariant.
6. **Demonstrate:** retain source/build IDs, workload, exact measurement boundaries, clock units, count/distribution of frame deltas, routine elapsed costs and missed deadlines, memory/code changes, plus game-state/capture checks. A finite recorded passage establishes the result for that passage. Report worst observed time, not an unproved universal maximum.

The learner should be able to explain why the change helped, what it cost and what evidence would contradict the explanation. Success is not a lower number alone. Reuse this exercise’s short evidence table in Starfield’s idle/new-note comparison, Dash’s normal/HUD-change comparison and Flock’s quiet/retrigger comparison, with their own tools and machine contracts.

## Modern tools as later depth

For the native emulator, an optional macOS route can use Instruments CPU sampling and call-tree views to locate host work, interval instrumentation to correlate it with a frame/audio delivery, and allocation tracking if heap churn is implicated. Sampling estimates where time is spent; it is not an exact invocation count or proof that a short rare routine never ran. A blocked or waiting thread may explain latency without dominating sampled CPU. See Apple’s [call-tree guidance](https://developer.apple.com/documentation/xcode/analyzing-cpu-profiles-with-call-tree-views) and [performance instrumentation](https://developer.apple.com/documentation/os/recording-performance-data). These are supported tool families, not a claim that this emulator already contains signposts or that the learner has Instruments installed.

For a browser lesson or WASM emulator, use a DevTools performance recording to relate scripting, rendering and frame-time spikes; inspect call trees and a separate allocation recording when a memory hypothesis warrants it. Main-thread work, worker execution and audio delivery may need different capture surfaces. Verify the browser version and worker/WASM symbol support first. See [Chrome’s Performance reference](https://developer.chrome.com/docs/devtools/performance/reference) and [allocation profiling](https://developer.chrome.com/docs/devtools/memory-problems/allocation-profiler). No browser feature here is presented as a guest-cycle counter.

For guest programs without a dynamic allocator, track static buffers, stack bounds, entity-pool occupancy and ROM/RAM size instead of pretending host allocation stacks describe guest memory use. A later OS-based Amiga allocation investigation needs a separately checked guest instrumentation method. Optional host optimisation must retain emulation fidelity: removing emulated work, reducing audio accuracy or dropping guest frames is a changed product contract, not an equivalent speedup.

## Evidence and completion rules

The [testing and diagnosis progression](testing-and-diagnosis.md) supplies the shared hypothesis, reproduction and regression method. A timing repair must preserve the game’s required behaviour as well as improve the measured deadline.

Use the [ownership and overload exercises](scheduling-ownership-headroom.md)
when a missed deadline comes from conflicting requests, publication or backlog.
Reducing total CPU cost alone may not repair those failures.

Use one small table per comparison: build/configuration; scenario and seed/input schedule; measured boundaries and units; sample count; typical and maximum observed cost; deadline misses; instrumentation; memory/code change; correctness checks. Add percentiles only with enough samples and an explained calculation. Preserve rare events individually; an average can conceal the one frame that matters.

Capture the event that glitches, not merely the whole session’s busiest routine. Consider dispatch delay, blocking, missed flags, resource conflicts and wrong scheduling before blaming raw CPU cost. Change one suspected cause, predict the result and measure again. Keep correctness checks separate from timing evidence, including audio articulation and game behaviour. Explain trade-offs in memory, code size, clarity and fidelity rather than teaching optimisation as a universal improvement.

Hardware markers and accounting should cite the primary register/timing references used by the [timing plan](timing-and-interrupts.md): Spectrum ULA/Z80, Commodore VIC-II/CIA and Amiga hardware manuals, and public NES PPU/DMA research. Tool source is authority for an implemented measurement surface, not hardware truth. Public Pattern Library additions follow a checked game implementation; Vault material supplies sourced period context without duplicating this plan. Use clear British English, “we” and recoverable experiments throughout.


## Foundations timing review

R4d revises From Source to Silicon05 and reconciles the module overview and the directly conflicting passages in units 02/03. The earlier unit-04 correction remains the basis: assembly provides control and responsibilities, not guaranteed speed or loss of all diagnostics. Interpreter descriptions now identify the simplified teaching model instead of asserting that every implementation reprocesses all source text on each visit. Display refresh and game updates are no longer equated.

The lesson uses explicitly invented milliseconds (A: 8/8/8/16, B: 10/10/10/10; deadline 12) to expose equal averages and different deadline outcomes. Both averages are 10; one of A's four updates misses, none of B's do. Predictions precede the answer; correctness and limited sample coverage remain explicit. No numbers are presented as course-game measurements.

The named later route links existing Meteor Storm units 19/20. Source inspection of `checkpoints/render-budget/meteor-storm.asm` confirms that the interrupt increments `frames`; main waits for alternate counts and stores the byte subtraction from `last_frame` in `frame_delta` before doing update work. The lesson therefore describes outer-loop sample spacing in interrupt counts, not simulation-step count, browser frame time or input latency. `MeteorExperiment.astro` exposes `frame_delta`; its embedded assembly runner and held boost controls already exist. This is an optional exploratory observation, not a new controlled benchmark or resumption of the deferred C05 companion. Existing native evidence remains owned by the Meteor Storm lesson and verification record.

The guidance removes a universal readable-frame-clock/BASIC assumption, explains clock resolution and wrap, distinguishes guest/host work, and acknowledges instrumentation and tool error. It makes no new hardware-rate claim or native execution claim. No machine samples, tools or WASM files changed. Reader trial and publication remain separate.
